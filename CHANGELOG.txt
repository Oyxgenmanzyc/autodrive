3.20 第二个创新点：风险时序注意力与决策时机

修改日期
- 2026-07-07

修改目的
- 从 origin/main 重新建立实验分支。
- 在不重写 DiffusionDrive、不改变 20 mode anchor 和原始 trajectory 主 loss 的前提下，引入历史风险趋势，让模型更关注跟车场景中的刹车时机和所需减速度。

涉及文件
- navsim/agents/diffusiondrive/modules/risk_utils.py
- navsim/agents/diffusiondrive/modules/risk_attention.py
- navsim/agents/diffusiondrive/modules/risk_gate.py
- navsim/agents/diffusiondrive/transfuser_features.py
- navsim/agents/diffusiondrive/transfuser_model_v2.py
- navsim/agents/diffusiondrive/transfuser_loss.py
- navsim/agents/diffusiondrive/transfuser_config.py
- navsim/agents/diffusiondrive/transfuser_agent.py
- navsim/planning/script/config/common/agent/diffusiondrive_agent.yaml
- tests/test_diffusiondrive_risk_utils.py
- tests/test_diffusiondrive_risk_attention_gate.py

核心改动
- FeatureBuilder 仍只使用推理阶段可用的 AgentInput，不使用 GT agent box 作为模型输入。
- 新增 LiDAR 前方走廊 gap 代理，从 4 帧历史 LiDAR 和 ego 状态构造 history_risk_tokens。
- 显式计算 THW、TTC、DRAC、delta THW、delta TTC、delta DRAC，避免让网络从零学习风险公式。
- TargetBuilder 使用训练阶段可用的 GT 历史 box、velocity、track_tokens 生成 memory auxiliary labels，仅作为监督信号。
- 新增 HistoricalRiskTemporalSelfAttention，将 history_risk_tokens 编码为 history_risk_memory。
- 新增 TemporalRiskCrossAttention，让 step-level trajectory query 查询历史风险记忆，再聚合回 mode-level feature。
- 新增 memory auxiliary loss，监督 risk trend、urgency、brake need 三个风险语义。
- 新增最终 risk gate，在 decoder 输出后按 safe、warning、dangerous 分组重选 mode，避免使用 cls - lambda * risk 这种量纲混合分数。
- 所有新增功能都有 config flag 控制；TransfuserConfig 默认关闭，3.20 的 diffusiondrive_agent.yaml 显式开启前四个开关。

预期影响
- 历史 LiDAR gap 变化提供可评测输入下的风险趋势代理。
- history_risk_memory 负责表达过去 0.5s 到 1.5s 风险是否恶化。
- Temporal Risk Cross-Attention 让候选轨迹的每个未来时间点接收风险趋势条件。
- risk gate 在推理阶段优先过滤刹车过晚、减速度不足或前向间距风险过高的 mode。

测试/验证结果
- 已通过 Python AST 静态解析检查。
- 已通过 git diff --check。
- 本地 unittest 未完整运行：当前 Windows Python 环境缺少 numpy，报 ModuleNotFoundError: No module named 'numpy'。
- 完整训练与服务器验证待后续服务器 smoke test。

与论文撰写的关系
- 可作为第二个创新点 3.20 的第一版工程实现。
- 对应论文表述：显式风险量化 + 历史风险时序注意力 + 风险条件轨迹解码 + 最终安全门控。
- 保持输入/监督边界与原始 DiffusionDrive 一致：推理输入不使用训练标注，GT 历史 box 只用于训练辅助监督和离线诊断。

3.20 Stage 1: risk shadow evaluation
Date
- 2026-07-10

Purpose
- Diagnose the 3.20 hard-gate regression without changing the checkpoint or selected trajectory.
- Replace the static-obstacle and single-brake-spike assumptions with measurable dynamic-risk terms.

Core changes
- Added an inference-only shadow scorer with no trainable parameters.
- Fuses the historical LiDAR gap with the current predicted agent box only when both estimates agree.
- Rolls the lead vehicle forward with estimated velocity and bounded acceleration.
- Applies longitudinal clearance only while the candidate trajectory laterally overlaps the lead vehicle.
- Defines brake onset as at least two consecutive deceleration steps and penalizes excessive jerk/deceleration.
- Samples predicted BEV drivable probability as a soft cost; no GT map or GT agent box is used at inference.
- Shadow mode records the proposed mode but always returns the original classifier mode.
- Optional soft re-ranking remains disabled by default.
- PDM CSV output now contains per-token front-source, static/dynamic clearance, brake timing, comfort, map, and cost diagnostics.

Experiment defaults
- use_risk_gate=False
- use_temporal_risk_cross_attention=False
- use_risk_shadow_evaluator=True
- use_soft_risk_rescore=False

Verification
- Python AST parsing passed for all modified Python files.
- Torch unit tests were not run locally because the Windows Python environment has no torch installation.
- Server smoke test and navtest shadow evaluation are pending.

3.20.3 THW/TTC delayed-trigger counterfactual shadow
Date
- 2026-07-12

Purpose
- Trigger intervention only when waiting one 0.5-second decision step reaches a speed-dependent risk boundary.
- Prefer longitudinal braking corrections while retaining conditional lateral avoidance candidates.
- Avoid direct arithmetic mixing of classifier logits and bounded risk costs.

Core changes
- Added Mulder-style THW amplification of TTC with THWmin=0.5s, THWmax=2.5s, and TTCmax=10s.
- Added current and delayed-0.5s THW/TTC/DRAC estimation.
- Added speed-dependent T1/T2 boundaries derived from the car-following TM study.
- Split top-3 lower-risk candidates into longitudinal-like and lateral-avoidance groups.
- Prefer longitudinal correction; allow lateral candidates when no lower-risk longitudinal candidate exists, or in emergency when lateral risk is clearly lower.
- Added same-run counterfactual PDM scoring while keeping the original classifier trajectory as the actual output.
- Added diagnostics for time-risk trigger, candidate type, lateral change, heading change, and counterfactual PDM delta.

Verification

3.20.4 Safety-Pareto counterfactual shadow
Date
- 2026-07-12

Purpose
- Prevent map-only or numerical-noise cost reductions from selecting a trajectory that does not improve longitudinal safety.
- Convert candidate selection from mixed scalar-cost ranking to explicit safety qualification.

Evidence
- In 3.20.3, 35 counterfactual trajectories averaged -0.02095 PDM.
- Three new TTC failures had dynamic-clearance changes of -0.188 m, -0.014 m, and +0.005 m.
- Total-cost differences as small as 1e-6 could previously switch modes.

Core changes
- Added a safety cost containing only weighted dynamic-clearance and brake-timing costs.
- A top-3 non-base mode now requires at least 0.10 m clearance gain and 0.01 safety-cost gain.
- Map and comfort costs are vetoes with bounded regression tolerances; they cannot compensate for absent safety gain.
- Pareto-qualified candidates are ranked by safety-cost gain rather than mixed total cost.
- Conditional lateral avoidance is preserved but now compares safety gain.
- Added Pareto count, validity, clearance gain, safety-cost gain, map regression, and comfort regression diagnostics.
- Actual trajectory selection remains unchanged because this experiment is still shadow-only.

Verification
- Python AST parsing and git diff checks passed locally.
- Replaying the 3.20.3 CSV retained 9 of 35 candidates, removed all 3 new TTC failures, retained 1 collision fix, and produced a cumulative counterfactual PDM delta of +0.5293.
- PyTorch unit tests and navtest counterfactual evaluation remain pending on the NAVSIM server.

3.22 Isolated GT soft brake-timing supervision
Date
- 2026-07-13

Purpose
- Teach the GT-matched trajectory mode when to begin sustained deceleration without adding inference-time selection rules.
- Keep the change limited to brake-timing supervision so its effect can be measured independently.

Design
- Keep the 3.20 historical-risk encoder and memory auxiliary objective as the common experiment base.
- Disable the hard risk gate, soft risk rescore, risk shadow evaluator, and Temporal Risk Cross-Attention.
- Build a training-only TTC context from GT front boxes and track tokens; GT boxes never enter model features or inference inputs.
- Activate the loss only when the same front track is visible for at least two future frames, TTC is within a 1.0-second preparation band before the speed-dependent T1 boundary, and the GT ego trajectory contains at least two consecutive braking steps.
- Select exactly the same anchor-matched mode used by the original trajectory regression loss.
- Convert predicted and GT acceleration to a differentiable soft brake profile and compare both the instantaneous profile and cumulative onset curve with SmoothL1.
- Use a conservative 0.1 loss weight and only the final decoder layer; ordinary scenes receive exactly zero brake-timing gradient.
- Do not add constant-deceleration pseudo trajectories, dynamic-clearance loss, jerk loss, or new inference-time behavior.

Observability
- Log pre-risk coverage, GT sustained-brake coverage, active supervision rate, raw/weighted timing loss, GT/predicted onset, signed and absolute onset error, early/late rates, speed error, minimum acceleration, jerk magnitude, acceleration oscillation, TTC context, and continuous front-track length.
- Jerk and oscillation are diagnostics only and determine whether a later smoothness objective is justified.

Cache and training
- A fresh cache is mandatory because the target-builder cache name is now `transfuser_target_brake_timing_v1`.
- The experiment uses one physical GPU selected with `CUDA_VISIBLE_DEVICES=4`; Lightning receives `devices=1`.
- Gradient clipping at 1.0 is required because earlier long training exposed non-finite shared-decoder/agent-query values.

Verification
- Added focused tests for preparation-zone activation, zero normal-scene loss, and gradient isolation to the GT-matched mode.
- Local PyTorch tests are not run; server smoke test, cache build, and full training are pending.

3.22 training-readiness and success-metric audit
Date
- 2026-07-16

Purpose
- Remove static code paths that could prevent the experiment from training cleanly or falsely suggest success.
- Preserve the isolated brake-timing hypothesis, 20 anchors, classifier selection, and standard PDM evaluation.

Corrections
- Replaced the brake-timing zero-displacement vector norm with a FP32 epsilon-smoothed squared-distance square root, removing the mixed-precision undefined derivative at a valid stationary point.
- Switched B200 training to `bf16-mixed`; custom backbone attention now computes QK logits, softmax, and attention-value aggregation in FP32 before returning to the active dtype.
- Removed original-author absolute asset paths. Anchors and offline ResNet weights now resolve from explicit environment variables or `$NAVSIM_EXP_ROOT/pretrained`, with actionable startup errors.
- Versioned risk-history features as `transfuser_feature_risk_history_v1`; an old baseline feature cache can no longer silently omit `history_risk_tokens`.
- Versioned the refined front-track target as `transfuser_target_brake_timing_v2`; a complete cache rebuild is required.
- Training now fails immediately when either the train or validation cache resolves to zero compatible samples.
- A future front track now stops being continuous when it leaves the configured longitudinal/lateral front corridor.
- Enabled the documented 1.0 gradient-norm clipping in the default training config for long mixed-precision runs.
- Validation inference now reports brake-timing metrics for both the GT-anchor-matched candidate and the trajectory actually selected by the classifier.
- Epoch metrics are reduced from active-scene sums and counts across DDP ranks, so sparse active scenes are not diluted by zero-valued batches.

Failure indicators
- `val/brake_timing_active_count == 0` means the supervision/evaluation slice is invalid and no improvement claim is supported.
- `val/brake_timing_onset_abs_error_s` measures the supervised GT-matched candidate; `val/brake_timing_selected_onset_abs_error_s` measures the actual selected output.
- `val/brake_timing_selected_late_rate`, jerk, acceleration oscillation, and speed MAE expose timing gains that trade away comfort or motion quality.
- The experiment is unsuccessful unless the standard held-out PDM score improves over its baseline without regressions in safety/progress components; lower training loss alone is not a success criterion.

Verification
- Added tests for active-scene sufficient statistics, selected-trajectory diagnostics, front-corridor continuity, and incompatible cache names.
- Python AST parsing passed for all modified Python files; `git diff --check` passed.
- Standalone YAML parsing was unavailable in the local shell because PyYAML is not installed.
- Training and PyTorch tests were not run locally; server cache generation, smoke test, full training, and held-out PDM comparison remain required.

3.22.2 Lightweight anticipatory brake-timing supervision
Date
- 2026-07-18

Evidence
- The 3.22 checkpoint completed 100 finite epochs and scored 0.884617944 on 11,881 valid navtest scenarios.
- Against the available 3.11 token-matched CSV, the net gains were mainly drivable-area compliance (+0.00993) and ego progress (+0.00990); collision (+0.00181) and TTC (+0.00253) gains were smaller and not uniformly positive.
- Brake-timing supervision covered only 290 / 18,179 validation scenes (1.595%). Its mean GT onset was 0.0069 s, showing that the old gate mostly selected scenes already braking at the first future step rather than earlier preparation scenes.
- Final selected-trajectory jerk was close to GT (0.629 versus 0.538), acceleration oscillation was 0.0192, and minimum acceleration was close to GT (-1.45 versus -1.57 m/s^2). There is no evidence for adding a separate jerk or hard-deceleration rule.
- `risk_counterfactual_pdm_valid` was zero for every valid 3.22 PDM row and carried no diagnostic information.
- Historical risk memory was encoded and supervised, but Temporal Risk Cross-Attention was disabled. Therefore this memory had no path into trajectory decoding or inference selection.
- Its train loss remained nonzero (0.1565 to 0.0453) while global pre-clip gradient norms ranged from 119 to 1,367. Because clipping is global at 1.0, this disconnected auxiliary task could still perturb the scale of updates to the main model.

Core changes
- Disable historical-risk attention and memory auxiliary loss in the 3.22.2 experiment defaults. This removes the unused temporal encoder, four-frame risk feature construction, and historical sensor/cache requirement from the active model.
- Keep the original 20-mode classifier, trajectory regression, diffusion decoder, selected-mode logic, and GT soft brake-profile target unchanged.
- Extend the training-only context with current/delayed THW and project the observed 0.5 s TTC/THW trend over a 1.5 s anticipation horizon.
- Activate timing supervision when a continuously tracked front vehicle is projected to enter either the speed-dependent TTC preparation boundary or THW <= 2.0 s, and the GT trajectory contains sustained braking.
- Normal samples and risky samples without GT sustained braking still receive zero brake-timing gradient.
- Replace the always-zero counterfactual PDM column with output-only braking diagnostics: onset, minimum acceleration, jerk, acceleration oscillation, final speed, and progress. These diagnostics require no GT and do not change trajectory selection.

Cache and verification
- The target schema is versioned as `transfuser_target_brake_timing_v3`; a fresh cache is mandatory.
- The feature builder returns to the baseline `transfuser_feature` schema because historical risk tokens are no longer model inputs.
- The experiment YAML retains the server-validated 3.22 defaults: lr=3e-4, batch_size=32, and num_workers=16.
- Local execution tests are not run by default. Server cache generation, focused unit tests, full training, and held-out PDM evaluation remain required.
